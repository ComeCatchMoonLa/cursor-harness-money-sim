# Cursor Agent Harness · 本实验备忘（5～10 条）

> 我自己的短笔记，供本仓 Agent 参考。
> 相关背景：Cursor · What we've learned building cloud agents — https://cursor.com/blog/cloud-agent-lessons

1. **Cloud Agent 的本质是「环境 + 闭环」**，不是把本地 Agent 搬到云上。写得出代码但跑不了测试，闭环就不存在。每个小目标开始先读 `PROGRESS.md`、git log 和 `docs/dev/FEATURES.json` 的未通过项；能启动就冒烟，失败先修。定栈后把安装写进 README；只有后续会话确实缺依赖时，再写 `.cursor/environment.json` 的 install。
2. **只在本仓写代码**。不碰其他仓（尤其不碰 CardRPG）。可以只读看公开标本。不要改本仓以外的其他项目；本仓内依赖和测试输出可以写。
3. **允许向本仓功能分支 push、开或更新 PR**，小步就可以，避免进度只留在本地。未达 DoD 时 PR 标明未完成。仍禁止 force-push、push `main`、自行合并、改其他仓（尤其不碰 CardRPG）、接真实券商/支付/账户或提交这类密钥。需要越权时先停，在 `PROGRESS.md` 写原因，等人类。质量未过不是越权，继续做并可以 push。
4. **自主选栈**：技术栈、目录结构、数值公式全由 Agent 决定，不要反问人类用什么框架。
5. **体量是小型模拟/经营游戏，不是技术 Demo。** V1 就必须可独立游玩（开局→中期→终局、核心行动不是摆设、约 9 年里有取舍），不是最小 POC。V2、V3 是新系统或经济结构明显变厚，不是补丁。V3 应多系统咬合、阶段策略会变、有风险与代价，不是三个按钮轮流点。仍零美术、文字/面板向，不接真钱、不做联机上架。修编译、改常数、补 README、小 UI 抛光可夹在版内，不能单独算一版。
6. **大目标拆细，小步慢跑**。开工前把版本命题拆成小目标清单（`PROGRESS.md` 或临时 plan）。每个小目标内部按顺序走：分析对齐 → 按需调研 → 短设计 → 实现 → 测试 → 自评审 → 小步 commit。禁止没写本小步设计要点就大面积写代码，也禁止 V1 前先写不可执行的长设计；设计远长于实现与测试就停笔去写代码并验证。未完成测试和自评审，不得宣称该小目标完成。质量手段不可省：设计阶段 3～5 条验收用例并勾完、全量回归保持绿色且不可删保护、改经济必跑模拟、UI 与引擎同一状态、`docs/dev/评审/BUGS.md` 里严重缺陷未关不得收工、检查表禁止只写 LGTM、PR 要带证据。100 局太慢就先优化模拟，不要堆新系统。收工按 Definition of Done：可玩路径通、相关测试绿、版本命题已写入、自 review 过 ACCEPTANCE、有手玩记录。缺一项继续本版。小步可以 commit 并 push 功能分支；未收工的 PR 标明未完成，不要自行合并。删掉本版新东西若不明显变薄，不算大版本。非 Demo 硬标准命中则不算完成。三种模拟策略里至少一种要极端，用来找洞。版级自 review 四问、决策密度和手玩记录写入 `PROGRESS.md`。规则撞车时：先可玩完整环，再测试/模拟，再按命题加厚；时间紧可减系统，不可减反馈闭环和 DoD。review 是自己的质量闸，不是等人过门。宁可少做一个花哨系统，也不要跳过测试/review。系统可以厚，但缺反馈先补闭环再加厚，不得用「先做个 Demo」永久停在半成品。V2、V3 的反馈要推动规则或系统级改动，而不是微调数值交差。
7. **反 Goodhart**：不许靠降低难度 / 抬高所有收益 / 取消风险来刷指标；要解释经济为什么有取舍。
8. **人类只在越权、高危、卡死、明显失控时介入**。前三版的正式验收在 V3 之后，不是在 V3 停。V3 之后按 `HARNESS.md`「做到 V20」筛选。人类不审每一版。小步自评审之后就 push。某一版标完成前，换一个没写过该 diff 的会话做交叉审核，只评论、不改分支、不合并。同一次会话自审不算交叉审核。细则在 `HARNESS.md`「PR 审核」。
9. **references/ 是随手翻的知识，不是必读作业**；examples 只许学结构，禁止整仓复制。
10. **诚实**：做不到的（比如批量局数上不去）就在 `PROGRESS.md` 写清瓶颈，不要掩盖。写下来不等于本版完成；DoD 缺一项就继续本版。后半程策略熵崩塌必须当洞察修规则，不能只记一笔。
