# Effective harnesses for long-running agents（公开要点摘录 / 我的短笔记）

> 来源：Anthropic · Effective harnesses for long-running agents
> https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
> 说明：中文摘录与个人笔记，非原文照搬。

## 核心观点

长程（跨很多步、可能跨会话）的 Agent，最大风险是**上下文丢失**和**中途漂移**。有效的做法：

- **进度文件（progress file）**：把「已完成 / 当前状态 / 下一步 / 踩过的坑」持久化到磁盘，让后续会话能接着干，而不是每次从零理解。本仓对应 `PROGRESS.md`。
- **增量推进**：一次只推进一小步并留下**干净、可继续的状态**（能跑、能测），而不是憋一个大改动。
- **少打断人类**：Agent 应尽量自主完成「做 → 验 → 改」，只在真正越权 / 卡死时才求助。
- **明确的完成判据**：让 Agent 知道「什么时候算这一轮做完了」，避免无限打磨或提前收工。

## 对本实验的启发

1. `PROGRESS.md` 每版要有版本命题（相对上一版新增的实质能力）和四行（What I learned / failed / changed / Why）。四行要写清「上一版测试/模拟 → 本版改了哪条规则或哪个系统」，不能只写调了哪个常数。
2. V1→V2→V3 之间**不设人工验收门**。三版仍须是三个大版本（各有版本命题），不是把「增量」理解成后两版只修 bug、调参数、改文案，也不是把 V1 做成最小 POC。V1 就要可独立游玩；V2、V3 把经济明显变厚。大版本内部才是小步：开工前拆细，验证通过再下一步，不要一次塞进未验证的大改动。缺反馈先补闭环再加厚，不得因此永久停在 Demo。
3. 每个小目标先写要点级调研/设计，再实现；不要没设计就大面积写代码，也不要先写长篇设计。写完就测，测完再自评审，然后小步 commit，并 push 本仓功能分支。本版收工前须同时满足 Definition of Done（可玩路径通、相关测试绿、版本命题已写入、自 review 过 ACCEPTANCE、有手玩记录）。缺一项继续本版，不进下一版。未收工可以更新 PR，但必须标明未完成，不要自行合并。测试未绿不能写成「可接受」后收工。不要把半成品标成「本版完成」。短 review 是自己的质量闸，不是等人过门。文档和检查表不能替代可运行的游戏、测试与模拟数据。验收用例未勾完、全量测试未绿、严重缺陷未关，都不得标完成。
4. 做不到批量模拟要在 `PROGRESS.md` 写清瓶颈。这不是把成品降成技术 Demo 并停住的理由。
5. 功能清单是 `docs/dev/FEATURES.json`，不是凭感觉宣布做完。只有按 steps 手玩或 UI 自动化（经济类还要有模拟）之后才能把 passes 改为 true。禁止删条目或把 steps 改容易。每个小目标开始先读未通过项并冒烟，冒烟失败先修。已经通过的条目若回归失败，立刻把 passes 改回 false，修完再做新功能。会话结束要留下可合并的 commit 和 PROGRESS 摘要，让下一轮不用猜。
